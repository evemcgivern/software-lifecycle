# Contributing

Thanks for helping. This project is maintained as time allows. Reviews are
best effort, with no promised response time.

## Report a product the tool could not match

Open the "Product the tool could not match" issue form. Give the public
product name, the publisher and the shape of the version string. Names
only. Never paste inventory rows, owner names or internal application names
into a public issue. Issues are public.

## Report a bug or ask for a feature

Use the bug report or feature request form. Use made-up (synthetic) rows if
you need to show input. For a security problem, do not open an issue. See
[SECURITY.md](SECURITY.md).

## Propose a code or docs change

1. Open or find an issue first. Its number is `NNNN` below.
2. Fork the repo, or make a branch if you have access.
3. Name the branch `type/NNNN-name`, for example `fix/0042-alias-typo`.
4. Make one change per commit. Write the message as
   `type(scope): summary`: lowercase after the colon, 50 characters or
   fewer, no period. The body explains why, not how.
5. Open a pull request into `main`. `main` is protected: a pull request is
   required and these five checks must pass: `test (3.9)`, `test (3.10)`,
   `test (3.11)`, `test (3.12)` and `test (3.13)`.
6. Fill in the pull request checklist.

## Run the tests

From the repo root, with no install step:

    python3 -B -m unittest discover -s tests

Do not pass `-t`. Running one module with `python3 -m unittest tests.test_x`
does not work here. Run one module like this instead:

    python3 -B -m unittest discover -s tests -p 'test_x.py'

If you have Python 3.9, run the suite on it too. The floor is 3.9.

## Ground rules

- Standard library only. No third-party runtime or test dependencies.
- Python 3.9 is the floor. Use no 3.10 or newer syntax (for example no
  `match` statements).
- No network use in `swlc/`. A test proves it. `refresh_data.py` is the only
  file that opens network connections.
- Error messages never contain inventory content.
- Wording: the tool says "needs review", never "vulnerable". Never call a
  release "signed". Keep the claims line and the KEV line exactly as they
  are in the code and README.
- Files under `data/` are generated by `refresh_data.py` and the workflows.
  Do not edit them by hand. The one exception is `data/aliases.json`. Every
  alias needs a source URL, a corpus row (a name that must match) and a
  negative corpus row (a name that must not). See "Extending the alias
  table" in [docs/usage.md](docs/usage.md).
- The docs are tested. Change docs and tests together.
- Report format promise: see [docs/report-schema.md](docs/report-schema.md).
  Adding a state, a list, a reason code or a decision code bumps
  `schema_version`.
- Workflows: pin every `uses:` to a full commit SHA, keep permissions
  minimal, and never use `pull_request_target`.

## What we will not accept

- Network calls in `swlc/`.
- New dependencies.
- Hosted-service features.
- Changes that make real inventory data leave the machine.
- Vulnerability scanning or CVE severity. This is not a scanner.

## Conduct

Be respectful. No harassment. The maintainer may close or lock a thread.
To raise a conduct concern, use the private reporting channel described in
[SECURITY.md](SECURITY.md), or contact the repo owner through their GitHub
profile.

## Labels the maintainer creates

The issue forms apply these labels: `bug`, `enhancement` and
`alias-request`.
